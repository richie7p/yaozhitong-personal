## 約五分鐘的展示流程

下列是在兩份固定來源完成的功能順序；目前雙擊 **`啟動研討會展示.cmd`**，使用獨立 `.local/seminar-demo-luna-20261020`，預載 Luna 修正後第三批首輪的真實生成結果與既有答案（4 條說明、3 題、7 次引用）。展示副本僅另補入經版本／SHA 核對的完整官方主檔 66,509 筆，生成內容與任務保持原值；啟動器會先做資料與來源檢查，原始驗收目錄完全未改。已答對題目可重新選錯、閱讀引用後再答對。啟動路徑、合成雙藥袋及現場備案見 [SEMINAR.md](SEMINAR.md)。

1. 在帳號設定填寫虛構成人資料。個人化分支可使用虛構「氣喘」狀況搭配咳服仿單；酵素膠囊沒有這項對應警語，應維持一般說明。這是來源關聯測試，不用來判定個人是否適合服藥。
2. 新增藥品：使用虛構藥袋辨識，或搜尋以上藥名。逐欄核對虛構用法後儲存；畫面上的劑量／頻次來自這份紀錄。
3. 在「我的藥品」開啟仿單說明。閱讀「藥品用途」「你已確認的用法」「與你相關的注意事項」，展開原文核對。個人化標示需同時通過健康資料比對及來源相關性核對；一般警語完整保留在下方。
4. 第一題先選錯，展示「依仿單原文」的解釋與可直接閱讀的引用。重答後進下一題；每次提交都保存到後端。
5. 到「用藥小教室」查看藥名與進度。重新整理、登出再登入，或再次在藥品頁開啟說明，都恢復既有已提交答案；內容仍有效時不另建立 AI 任務。完成後可重新複習。
6. 未完成測驗時設定提醒並打卡，確認兩個流程獨立。問答頁只產生回答；等待或失敗時可從「AI 處理紀錄」查看或使用原輸入重試。
7. 修改健康資料，確認小教室隱藏舊內容；正在開啟的舊測驗提交時會停止並要求重新產生。另以未匹配許可證的虛構藥品展示「資料不足」，仍可查看已確認用法。

## 實作與相容性

- `Claim.category` 為可選的 `purpose | use | warning | other`；旧內容沒有分類時保留一般說明。
- `profileRefs` 是可選的 `{field,value}[]`，欄位限 age、sex、conditions、allergies、pregnancy。只有當次健康資料的明確值可供引用；未知值、姓名與 notes 不作標示依據。參照限警語，先核對值，再獨立核對來源相關性；相關性失敗時移除標示，一般內容依自身核對結果保留。
- 生成版本為 `grounded-v9-source-quote-explanations`。模型選擇來源段落編號並複製系統預先標記的欄位／必要條件；後端帶入連續原文並繼續核對語意，短引用仍維持 8 字門檻。生成省略已識別的成分／機轉／一般用法等背景段落；獨立語意審核只看本項自身引用與必要父條件，不借用未引用上下文。解釋由已確認的本題引用組成並標記 `explanationKind=source_quote`。警語不能只由成分表推論，病史直接字串符合只提出相關性候選。新衛教最多兩題，核對包含全部選項；chat／interaction 不產生測驗。舊版本內容與答案保留作歷史紀錄，規則失效後不供目前作答。
- 單題／整份提交均使用原答題 API，交易內合併答案、核對 UID 與各資料版本。未作答與答錯分開記錄；無測驗的內容顯示「尚無測驗」。
- 私人進度留在後端，沒有新增健康資料 localStorage／Service Worker 快取。沿用儲存介面，後續可接正式登入、Firestore、背景工作及推播。

### 1. 出題先限定學習重點，再檢查每個選項

現有生成與審核提示已要求唯一答案，但真實輸出仍有歧義；下一輪需增加資料結構與後端檢查，不能只追加提示詞。

1. 第一版只出「用途」與「注意事項」的理解題，每份最多兩題。有效成分背誦、作用機轉、劑量及頻次不列入這輪出題範圍。原有使用者確認的用法繼續直接顯示。
2. 為兩份固定仿單整理可追溯的來源欄位與條件，例如「適應症」「警語」，記錄來源版本、段落與原文。這是測試用標註，不等於新增藥師審核。
3. 候選題以 `claimId` 連到同一份內容中的衛教說明，另保存 `learningObjective`、`sourceSection`、`requiredConditions`。可在同一次生成提出候選，但最終必須等說明與題目各自通過核對才發布，避免無條件增加模型呼叫。
4. 審核結果由單一布林值擴充為逐選項判定與理由，區分「來源支持」「來源矛盾」「無法判定」。核對範圍須符合題目指定的欄位及適用條件；不能拿作用段落替代適應症欄，也不能把來源沒寫當成醫學上的錯誤。
5. 只發布唯一答案明確、解釋有引用且未漏條件的題目。來源沒有支持、選項可能同時成立、條件有爭議、所依據的說明被排除時，捨棄該題並記錄原因。不足兩題可只顯示一題；全部不合格時顯示已核對衛教與「暫無可用題目」。
6. 對固定、已核對的來源欄位，可使用限制句型，例如「依仿單『適應症』欄，本品的用途是什麼？」。若使用人工標註或規則產題，驗收報告標明產生方式，不將其列為模型自行產題成功。

三個既有問題的處理：酵素成分題退出成人衛教題目範圍，但保留為多解反例；咳服用途題限定「適應症」欄；咳服警語題保留「氣喘所引起之咳嗽」條件。原始錯題留存，不直接修改驗收資料庫來製造通過結果。

建議修改位置：`server/ai.ts`、`shared/schema.ts`、`tests/nvidia.test.ts`。前端只顯示已核對結果；審核理由留在診斷資料中。

### 2. 個人化顯示相關性，不推斷未填寫的事實

- 只使用當次明確填寫的健康資料。引用中的因果、時間、劑量或其他適用條件，不得因卡片摘要而省略。
- 例如填寫「氣喘」可提示讀者查看相關仿單警語，但不能據此斷言目前症狀由氣喘造成，或直接給出個人用藥結論。
- 重點卡及完整已核對說明都保留相同限制；展開原文可追到相同來源。相關性核對失敗時移除個人化標籤，內容仍需通過一般衛教核對才可保留。
- 增加未填健康資料、無關健康資料、符合其中一個「或」條件、條件包含否定等測試。文字關鍵詞只能輔助檢查，不能單獨作為通過證據。

建議修改位置：`server/ai.ts`、`src/Evidence.tsx`、`tests/learning.test.ts`、`tests/nvidia.test.ts`。

### 3. 更新規則後，舊題確實停止使用

目前生成快取包含 `GROUNDING_VERSION`，但 `LearningRecord` 與 `learningCurrent()` 沒有對應的生成規則版本檢查；因此只更新提示版本，藥品頁仍可能恢復舊題。

- 第一版新增單一 `contentVersion`，代表影響內容正確性的生成／核對規則；寫入快取結果與學習紀錄。純排版變更不提升此版本。
- 列表、藥品頁恢復內容及答題交易均檢查此版本，沿用現有健康資料、藥品及來源版本檢查。建立新內容時也檢查任務使用的版本，避免舊任務完成後被當成新版內容。
- 沒有版本欄位的既有紀錄視為需要更新，保留原始內容與答案供歷史追溯，但不作為目前可作答內容。前端提供明確的重新產生入口。
- 新內容建立新的紀錄與答案集合；即使題目仍叫 `q0`、`q1`，也不能搬移舊答案。舊頁面提交回傳 `stale_content`，提示含「內容規則已更新」。
- 同時測試：只改規則版本、健康資料變更、藥品修改、仿單更新、舊分頁提交與更新中的背景任務。

建議修改位置：`shared/schema.ts`、`server/domain.ts`、`src/MedicationViews.tsx`、`src/Evidence.tsx`、`tests/learning.test.ts`。

### 4. 生成穩定性與畫面回饋

- 處理紀錄顯示準備來源、產生內容、核對依據等實際階段，不顯示沒有計算依據的百分比。離開頁面後可從原任務返回。
- 將連線／網路錯誤、讀取本文逾時、服務繁忙、JSON 無效、輸出截斷及證據核對失敗分開記錄。現有 `response.json()` 也納入逾時與錯誤處理。
- 先設定可調整的任務整體期限，暫定 180 秒，涵蓋所有階段與重試。須同步檢查 worker lease／續租，避免期限尚未到就被重複執行；可用模擬時鐘驗證，不需每次等待三分鐘。
- 格式復原先處理已知格式包裝；仍無法通過結構驗證才考慮最多一次額外請求。每次任務執行暫定最多 6 次模型 HTTP 請求，生成、審核、格式復原及 HTTP 重試共用此上限與剩餘期限，不形成巢狀無限重試，也不放寬引用核對。使用者重試另計一次執行，完整記錄同一任務的累計用量。
- 規則版本過期的成功任務需建立新版內容；失敗任務沿用原任務重試，不繞過既有三次執行上限。
- 文案「完整仿單說明與注意事項」改為「已核對的說明與注意事項」，準確區分生成說明與完整原始仿單。保留全部已核對警語，並提供原文入口。
- 沒有合格題目時顯示「目前可閱讀說明，暫無可用的理解題」，進度維持不可測驗；提醒與服藥紀錄保持可用。

建議修改位置：`server/ai.ts`、背景任務執行與 lease 邏輯、`src/JobHistory.tsx`、`src/Evidence.tsx`、`tests/nvidia.test.ts`、`tests/e2e/learning.spec.ts`。

### 本輪驗收設計

**軟體回歸：** 執行 `typecheck`、`check:local`、正式建置。新增測試聚焦版本失效、錯題放行、個人化條件與錯誤復原；保留桌面／375px、鍵盤、重整與重新登入、提醒獨立的既有測試。模擬模型的通過結果只證明程式分支符合預期。

**真實內容：** 預先固定「兩款藥 × 三種資料情境（未填健康資料／明確氣喘／與來源無關的虛構條件）× 各兩次獨立生成」，共 12 個衛教任務，避免命中快取。再跑原有一次辨識及兩款藥各一則有來源問答，共 15 個模型任務；缺少來源另測且不呼叫模型。這是下一輪評估範圍，尚未執行。每任務可能包含多次模型請求，紀錄 HTTP 次數、tokens、耗時、規則／來源／模型版本及失敗原因；費用不以任務數推算。格式復原及重試亦計入紀錄。

**品質判準：** 每個實際顯示的題目都逐題對照來源，核對唯一答案、所有選項、條件、解釋及衛教關聯；個人化另核對使用了哪些明確資料。既有三種錯誤及保留評估集不能被錯誤放行，同時要有正例確實保留。兩款藥各須在重複生成中產出可完成主流程的合格理解題，不能靠把所有題目刪除來宣稱品質通過。

報告列出「候選題數／拒絕題數／顯示題數／人工核對合格題數／無題目任務數」，並分開列 API 完成與來源品質。完整保存失敗樣本；不能只挑成功的一輪。小樣本呈現實際分子、分母與耗時範圍，不宣稱已證明長期準確率或臨床安全。

**交付判定：** 若顯示內容仍有多解、來源不支持、條件省略或錯誤個人化，維持 `partial_pass` 並列出具體項目。通過時也只標記本輪固定資料的軟體與內容驗收通過；兩份仿單及醫療內容的藥師審閱另行記錄。
